# Auth: library choice (Lucia vs Auth.js), identity scope, workspace onboarding

- **Label:** `wayfinder:grilling`
- **Status:** closed (resolved 2026-07-28)
- **Parent:** [0001 — MAP](./0001.md)

- **Assignee:** ZCode (working the map)

## Question

The map has committed to **email/password as the baseline, pluggable OAuth (Google/GitHub), self-hostable, HTTP-only cookie sessions**, with RBAC layered on as app logic. This ticket resolves the remaining auth decisions:

1. **Library: Lucia vs. Auth.js (NextAuth v5).** Pick one for v1 with rationale. Considerations:
   - **Lucia** — lightweight, session-library (not a framework), full control, trivially self-hostable, but the author announced end-of-maintenance (early 2025); community forks exist. Confirm current maintenance status during resolution.
   - **Auth.js / NextAuth v5** — mature, framework-integrated with Next.js App Router, broad provider support, active maintenance, but heavier and more opinionated.
   - Recommendation given the self-hostable + multi-tenant + pluggable-OAuth requirements: state the choice and the reasoning. If Lucia's maintenance status is a real risk, that's decisive.
2. **Identity scope: global account vs. workspace-scoped.** Is a `user` a global identity (one login, member of N workspaces) or scoped per workspace (separate account per workspace)? The data model (ticket 0003) needs this. **Recommend global** (Notion-like: one account, many workspaces) — confirm.
3. **Workspace provisioning.** Can any signed-in user create a workspace, or is creation admin-gated (matters for self-host: should the first user be auto-promoted to owner)? **Recommend** any user can create; first user on a fresh install becomes owner of a default workspace.
4. **Joining a workspace.** How does a user join — invite link (token), email-domain allowlist, or both? **Recommend** invite link (token, expiring) as the v1 mechanism; defer email-domain allowlist to post-v1.
5. **Password security specifics.** Confirm: argon2/bcrypt hashing (auth library provides), password reset via email token, rate-limiting on login. State the baseline so the spec is complete. Email *sending* — does v1 need a configured SMTP / transactional email, or can reset be deferred? (If reset is in scope, an email transport becomes a dependency.)

**Resolve by:** `/grilling`, with a `/research` touch for current Lucia maintenance status (item 1). Output: the chosen library with rationale, the identity model, the workspace-provisioning rule, the join mechanism, and the password/email baseline.

## Notes

- **Identity scope (item 2) feeds the data model** (ticket 0003): whether `users` is global or per-workspace changes the schema. The two tickets should reconcile.
- If **email sending** is required (password reset), it's a new infra dependency for a self-hostable app — surface that as a downstream concern.

## Resolution — 2026-07-28

All five questions resolved. Research findings at
[`../research/0006-auth-libraries.md`](../research/0006-auth-libraries.md) —
key result: **Lucia is deprecated (no successor) and Auth.js v5 is still beta
with its maintainers redirecting new projects to Better Auth**, so the real
2026 choice is Better Auth.

### Decisions locked

1. **Library: Better Auth** (`1.6.x`, actively shipped). Built-in email/password
   + pluggable OAuth (Google/GitHub) + DB-backed **HTTP-only cookie sessions**,
   fully **self-hostable** (zero cloud accounts required), TS-first, Next.js
   App-Router integration. RBAC/groups/shares remain app logic on top
   (Better Auth owns authentication; authorization is OpenNote's permission
   engine from ticket 0002). Chosen over: Lucia (deprecated, no successor),
   Auth.js v5 (perpetual beta, maintainers point elsewhere).
2. **Identity scope: global** (confirmed, matches ticket 0003 + CONTEXT.md) —
   one `users` account, many `workspace_members` rows. Better Auth's user
   table is the global identity; `workspace_members` is the role join.
3. **Workspace provisioning:** any authenticated user can create a workspace
   (becomes its Owner). **Fresh-install bootstrap:** the first user to sign up
   is auto-promoted to Owner of a default **"OpenNote"** workspace, so a new
   deploy isn't an empty shell. No CLI init step. Subsequent sign-ups create
   their own or join by invite.
4. **Joining: invite links** — Owner/Admin generates a token-bearing invite
   (stored in `workspace_invites`, ticket 0003), expiring **7 days**, revocable.
   Invitee opens the link → if they have an account they're added at the
   invite's role, else they sign up then accept. Email-domain allowlist is
   **post-v1**.
5. **Password/email baseline:** argon2 hashing (Better Auth provides);
   **password reset via email token**; rate-limiting on login (Better Auth +
   a middleware-level limiter). **Transactional email IS in v1**, via a
   pluggable **SMTP transport** (env: `SMTP_HOST/PORT/USER/PASS/FROM`),
   self-hostable with any relay (Mailgun/SES/Resend/your mailserver). Two uses:
   password reset + invite emails. **Email verification on sign-up is optional**
   (off by default for self-host low-friction; auto-on when SMTP configured).
   **Fallback if SMTP unconfigured:** invite links are shown in the UI
   (copy/paste); password reset is disabled or operator-assisted.

### What Better Auth owns vs. OpenNote owns

| Concern | Owner |
|---|---|
| Credentials, password hashing (argon2), sessions, cookies | **Better Auth** |
| OAuth provider wiring (Google/GitHub) | **Better Auth** |
| Email verification, password-reset tokens, reset email | **Better Auth** (+ our SMTP transport) |
| `users` identity table | **Better Auth** (its schema) → referenced by our `workspace_members` |
| Roles, groups, shares, effective-permission engine | **OpenNote** (`packages/auth`, ticket 0002) |
| Workspace provisioning, invites, bootstrap | **OpenNote** |

### Downstream impact

- **0003 (data model)** — `users` is managed by Better Auth's schema; our
  `workspace_members.user_id` is an FK to Better Auth's user PK. Confirm the
  PK type (UUID vs. Better Auth's default) during the build so the FK matches.
  `workspace_invites` (ticket 0003) is the invite store.
- **0009 (monorepo)** — Better Auth config + the permission engine live in
  `packages/auth`; the SMTP transport in `packages/storage` (or a small
  `packages/email`); Next.js middleware for session + login rate-limit in
  `apps/web`.
- **Env additions:** OAuth provider creds (`GOOGLE_CLIENT_ID/SECRET`,
  `GITHUB_CLIENT_ID/SECRET` — optional), SMTP (`SMTP_*`), plus Better Auth's
  `AUTH_SECRET`. All part of the single-source env schema (ticket 0009).
- No other ticket depends on 0006's specifics; it is a leaf.

### 🔒 Security requirements (added post-resolution — see `research/SECURITY-REVIEW.md`)

1. **Invite tokens must be cryptographically unguessable.** Tokens are an
   account-onboarding path = account-takeover vector if predictable. Generate
   with `crypto.randomUUID()` or `crypto.randomBytes` (CSPRNG), **not** DB ids
   or timestamps. Expiring (7 days), revocable, and **single-use on accept**
   (`accepted_at` set; reject reuse). Rate-limit invite-accept per IP **and**
   per token.
2. **Email-control verification on invite accept.** Email verification is
   optional at sign-up, but **accepting an invite sent to email E must verify
   the accepting account controls E** (the account's email is verified-equal to
   E, or verification is forced at accept). Otherwise an attacker registers with
   a victim's email and steals their invite.
3. **OAuth account linking requires the existing session.** When a user with
   email/pw links an OAuth provider sharing the same email, linking must require
   the existing session — else an attacker registers a Google account with a
   victim's email and links into the victim's account. Verify Better Auth's
   `accountLinking` config enforces this (it does by default; don't disable).
4. **Password reset tokens:** single-use, short TTL (≤15 min), invalidated on
   use and on any successful login. Confirm Better Auth's defaults; don't extend.
5. **Login rate-limiting — per-IP AND per-account.** A single-IP limit is
   bypassable; a single-account limit prevents distributed spraying against one
   account. Apply both.
6. **First-user-bootstrap is a self-host assumption.** On a *public* deploy,
   "first signer-upper owns the default workspace" is a race. Document that
   public exposure requires gating sign-up (allowlist/invite-only) or seeding
   the owner out-of-band. The default config assumes a private/self-host network.

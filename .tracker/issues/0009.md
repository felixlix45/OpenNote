## Question

The stack is locked: **full-TypeScript monorepo, Next.js + Yjs/Hocuspocus + Postgres + S3, Docker-deployed.** This ticket resolves the **shape of the repo** so a builder knows where everything lives. This is mostly laying out the structure the other tickets' decisions live inside.

1. **Monorepo tool.** Pick **pnpm workspaces + Turborepo** (recommend) or **Nx**. Rationale: pnpm + Turbo is the current default for TS app monorepos; lightweight, fast caching. Confirm.
2. **Layout.** Propose the package/app split. Recommended:
   ```
   apps/
     web/            # Next.js app (UI + REST/route handlers + BlockNote editor)
     realtime/       # Hocuspocus WebSocket server (long-lived process)
     worker/         # (optional) background jobs — thumbnail gen, quota recompute
   packages/
     db/             # Prisma/Drift schema + client (shared by web + realtime + worker)
     auth/           # session/cookie helpers, RBAC permission engine (shared)
     shared/         # types, zod schemas, Yjs block schema shared across apps
     ui/             # shared React components (sidebar, cmd+K palette, block blocks)
     config/         # eslint/tsconfig/tailwind presets
   ```
   Confirm or adjust. Key decision: **is the Hocuspocus server a separate app/process or a route inside Next.js?** Recommend **separate** (`apps/realtime`) — it's a long-lived WebSocket process, doesn't fit Next.js's request model, and must be independently scalable.
3. **DB layer.** Confirm **Prisma** (recommend — TS-first, schema-as-source-of-truth, migrations) or **Drizzle** (lighter, more SQL-native). State the choice; it owns the schema defined in ticket 0003.
4. **Type & runtime safety.** Confirm: **TypeScript strict** everywhere, **Zod** for runtime validation at API boundaries, types generated from the Zod schemas in `packages/shared`.
5. **Env config.** Confirm a single-source `packages/config/env.ts` (Zod-validated `process.env` schema) consumed by all apps — so missing/invalid env fails at boot, not at runtime.
6. **Local dev.** Confirm `docker-compose.yml` at repo root running Postgres + MinIO (+ the app via the dev server), with seeded dev data. One-command `pnpm dev`.
7. **Testing baseline.** State the v1 testing bar: **Vitest** for unit (especially the permission engine in `packages/auth`), **Playwright** for e2e of the editor flow. No hard coverage gate for v1 — but the permission engine *must* have unit tests (it's the security boundary).

**Resolve by:** `/grilling`. Output: the chosen monorepo tool + DB layer, the confirmed directory layout (with the realtime-separate-process decision explicit), the env/config approach, the local-dev compose setup, and the testing baseline. This ticket unblocks the build — once it and the data-model + permission tickets close, a builder can scaffold.

## Notes

- The **realtime-as-separate-process** decision (item 2) is the one real fork here; the rest is convention. It must reconcile with the deployment topology (Docker, long-lived processes) already on the map.
- This ticket has no deep dependencies — it can be worked in parallel with 0002–0008 — but its *output* is the skeleton the build effort will populate.

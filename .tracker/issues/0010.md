# Realtime authorization: gating Hocuspocus connections & doc loads by effective permission

- **Status:** open
- **Parent:** [0001 — MAP](./0001.md)
- **Blocking:** none — **blocked by** [0002](./0002.md) and [0004](./0004.md)
- **Assignee:** _(unclaimed)_

## Question

Real-time is in scope, and every WebSocket connection to a page's Y-doc must be gated by the permission engine. This ticket resolves **how the realtime layer enforces authorization**, consuming the outputs of ticket 0002 (the effective-permission algorithm) and ticket 0004 (the Hocuspocus hook mechanics). It is the bridge between "what's allowed" and "what the editor enforces."

1. **Gating points.** Confirm the two enforcement points Hocuspocus exposes — `onAuthenticate` (reject the connection before any sync) and the doc-load path — and that we check at **both**: connection open *and* every doc load (a user's permission can be revoked mid-session). State the hook(s) to use, per ticket 0004's findings.
2. **Read vs. write vs. present.** The permission engine (ticket 0002) produces roles/permissions. Decide how that maps to Hocuspocus:
   - A **read-only** principal should receive the doc (read) but be blocked from producing updates.
   - A **none** principal must be rejected outright at `onAuthenticate`.
   - Confirm whether Hocuspocus supports a "read-only" mode natively, or whether we enforce write-blocking by rejecting updates in `onChange`/onUpdate when the connection is read-only. (Ticket 0004's research informs this.)
3. **Live revocation.** If a user's permission is revoked while they hold an open connection, what's the v1 behavior? Options: (a) kill the connection via Hocuspocus on the next permission re-check, (b) accept staleness until they reconnect. **Recommend (a)** with a periodic re-check (e.g. every 60s and on share-change event) — confirm. This is the security-critical behavior.
4. **Connection identity.** How does the realtime server know *which user* is connecting? Confirm the flow: the editor client obtains a short-lived realtime token (or uses the session cookie, if the WS origin matches) from the web app, presents it to Hocuspocus, which resolves user + page + permission. State the token mechanism (recommend: session cookie, since web + realtime share an origin behind the reverse proxy in the Docker topology).
5. **Cost budget.** The effective-permission algorithm (ticket 0002) must be cheap: confirm it runs in O(depth-of-tree) indexed lookups, cached per-connection for the re-check interval, so a 100-document workspace doesn't do 100 DB round-trips per keystroke. State the caching strategy.

**Resolve by:** `/grilling`, after tickets 0002 and 0004 are resolved. Output: the gating-point spec, the read/write/none mapping, the live-revocation rule, the connection-identity/token mechanism, and the cost/caching budget. **Blocked by 0002 and 0004** — it cannot resolve until the permission algorithm and the hook mechanics are both known.

## Notes

- This ticket is the **security boundary of the realtime layer**. It must be resolved (not deferred) for v1 to be safe; it is *not* fog — the question is sharp, just downstream of two other tickets.
- The "live revocation" decision (item 3) is the one product-visible behavior; the rest is mechanism.

# Realtime authorization: gating Hocuspocus connections & doc loads by effective permission

- **Status:** closed (resolved 2026-07-28)

## Question

Real-time is in scope, and every WebSocket connection to a page's Y-doc must be gated by the permission engine. This ticket resolves **how the realtime layer enforces authorization**, consuming the outputs of ticket 0002 (the effective-permission algorithm) and ticket 0004 (the Hocuspocus hook mechanics). It is the bridge between "what's allowed" and "what the editor enforces."

1. **Gating points.** Confirm the two enforcement points Hocuspocus exposes — `onAuthenticate` (reject the connection before any sync) and the doc-load path — and that we check at **both**: connection open *and* every doc load (a user's permission can be revoked mid-session). State the hook(s) to use, per ticket 0004's findings.
2. **Read vs. write vs. present.** The permission engine (ticket 0002) produces roles/permissions. Decide how that maps to Hocuspocus:
   - A **read-only** principal should receive the doc (read) but be blocked from producing updates.
   - A **none** principal must be rejected outright at `onAuthenticate`.
   - Confirm whether Hocuspocus supports a "read-only" mode natively, or whether we enforce write-blocking by rejecting updates in `onChange`/onUpdate when the connection is read-only. (Ticket 0004's research informs this.)
3. **Live revocation.** If a user's permission is revoked while they hold an open connection, what's the v1 behavior? Options: (a) kill the connection via Hocuspocus on the next permission re-check, (b) accept staleness until they reconnect. **Recommend (a)** with a periodic re-check (e.g. every 60s and on share-change event) — confirm. This is the security-critical behavior.
4. **Connection identity.** How does the realtime server know *which user* is connecting? Confirm the flow: the editor client obtains a short-lived realtime token (or uses the session cookie, if the WS origin matches) from the web app, presents it to Hocuspocus, which resolves user + page + permission. State the token mechanism (recommend: session cookie, since web + realtime share an origin behind the reverse proxy in the Docker topology).
5. **Cost budget.** The effective-permission algorithm (ticket 0002) must be cheap: confirm it runs in O(depth-of-tree) indexed lookups, cached per-connection for the re-check interval, so a 100-document workspace doesn't do 100 DB round-trips per keystroke. State the caching strategy.

**Resolve by:** `/grilling`, after tickets 0002 and 0004 are resolved. Output: the gating-point spec, the read/write/none mapping, the live-revocation rule, the connection-identity/token mechanism, and the cost/caching budget. **Blocked by 0002 and 0004** — it cannot resolve until the permission algorithm and the hook mechanics are both known.

### Decisions locked

1. **Gating points** — check in **`onAuthenticate`** (per ticket 0004, the hook
   with token/context access — *not* `onConnect`). `onAuthenticate` runs on
   every connection open AND every doc load (a user's permission can change
   mid-session). Owner/admin short-circuit to full access before the CTE runs.
2. **Read / write / none mapping** — the effective-permission level (ticket 0002)
   maps to Hocuspocus connection mode:
   - **none** (no grant on path, and not owner/admin) → **reject the connection**
     in `onAuthenticate` (the doc never loads).
   - **reader** or **commenter** → connection accepted with
     **`connection.readOnly = true`** (receives the doc + live updates from
     others; this connection's own updates are rejected — enforced in
     `onChange`/onUpdate by checking the connection's readOnly flag).
   - **editor** → **read/write** (`readOnly = false`).
   - **owner/admin** → read/write (bypass).
   Note the **two distinct checks** derived from one `effective(U, R)` call:
   `can_read` = effective ≥ Reader (gate to connect at all); `can_write` =
   effective ≥ Editor (gate to produce updates). The realtime server computes
   `effective` once per `onAuthenticate` and derives both.
3. **Live revocation — proactive kill on permission change.** When a share is
   removed, a group membership changes, a role is lowered, or a page/folder is
   deleted, the mutating endpoint — after committing — **emits an event** the
   realtime server subscribes to; the server closes the affected open
   connections. On reconnect, `onAuthenticate` re-runs `can_read` → the user is
   rejected or downgraded. **Latency ~1s.**
   - **v1 mechanism: Postgres `LISTEN/NOTIFY`** (no extra infra — the DB is
     already there). The mutating endpoint does `NOTIFY perm_change,
     payload::jsonb{userIds, pageIds}`; `apps/realtime` `LISTEN`s and closes
     matching connections.
   - **post-v1:** swap to a Redis pub/sub channel when `extension-redis` is
     added for horizontal scaling (ticket 0004).
   - **Residual risk:** if `apps/realtime` crashes between the mutation and the
     kill, a stale connection survives until the client reconnects/refreshes —
     bounded, not unbounded. Acceptable for v1; the alternative (periodic
     full re-auth) is heavier and achieves no better guarantee in the common
     case.
4. **Connection identity — session cookie.** The editor's WebSocket carries the
   same **HTTP-only Better Auth session cookie** set at login. `onAuthenticate`
   reads the cookie from the connection's initial HTTP headers, validates the
   Better Auth session (shared session logic in `packages/auth`, ticket 0009),
   and resolves the user. Works because **web + realtime share an origin**
   behind the reverse proxy (Caddy/Nginx in the Docker topology) — the browser
   sends the cookie to both `/` (web) and `/collab` (realtime WS). **Zero new
   auth surface** — reuses the existing session; no token minting/rotation.
5. **Cost budget — met.** `effective(U, R)` is O(depth) indexed lookups (the
   recursive CTE over `folders.parent_id`, plus the live `group_members` join,
   ticket 0003). It runs **once per `onAuthenticate`** (on connect and on each
   doc load), **NOT per keystroke** — Hocuspocus syncs updates without
   re-checking auth mid-connection (revocation is handled by the proactive
   kill, item 3). For a connection editing one page, that's one CTE per load —
   cheap. No per-connection permission cache needed in v1.

### The end-to-end realtime auth flow (spec)

```
1. Browser opens WS: ws://app/collab/page:{pageId}
   - carries: Cookie: <Better Auth session>
2. Hocuspocus onAuthenticate(data):
   a. session = validateBetterAuth(data.requestHeaders.cookie)  // packages/auth
      if invalid -> reject (no user)
   b. user = session.user
   c. pageId = parseDocName(data.documentName)                   // "page:<uuid>"
   d. role = workspaceMemberRole(user, workspaceOf(pageId))      // owner/admin/member/guest
   e. if role in (owner, admin): return ctx { user, pageId, level: 'manage', readOnly: false }
   f. level = effectivePermission(user, pageId)                  // the CTE, ticket 0002/0003
   g. if level == none: -> reject
   h. readOnly = (level in (reader, commenter))
   i. return ctx { user, pageId, level, readOnly }
3. Editor connects; doc loads; updates flow (readOnly conns' updates rejected in onChange).
4. [permission changes elsewhere] -> NOTIFY perm_change -> realtime closes ctx's connection
   -> browser reconnects -> step 2 re-runs -> rejected or downgraded.
```

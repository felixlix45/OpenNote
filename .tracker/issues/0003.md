## Question

Given the locked decisions — **hybrid storage** (one Y-doc per page is the source of truth for body content; PostgreSQL holds the tree + RBAC + a denormalized `body_text` for search), **multi-tenant workspaces with groups and permission inheritance** — this ticket resolves the **exact relational schema** for v1. Produce SQL-level table designs (columns, types, foreign keys, indexes) and the rationale for each non-obvious choice.

Tables to design (at minimum):

1. **`users`** — global account vs. workspace-scoped identity (see fog; this ticket should propose, the auth ticket should confirm). Profile fields, credentials reference (auth library owns password hashing).
2. **`workspaces`** — the tenant boundary. Owner, name, slug, plan/quota fields.
3. **`workspace_members`** — user × workspace × role (the join that resolves "who's in this workspace and as what").
4. **`groups`** and **`group_members`** — groups live inside a workspace; many-to-many with users.
5. **`folders`** — `parent_id` self-reference for nesting; belongs to a workspace.
6. **`pages`** — `folder_id` *and/or* `parent_page_id` (nested pages); `title`; references its Y-doc.
7. **`page_docs`** — `page_id → Yjs binary blob` (the editor's source of truth). Decide: `bytea` column vs. separate blob table; how updates are written.
8. **`shares`** — the ACL rows: `(resource_type, resource_id) × (principal_type, principal_id) × role/permission`. Encodes the inheritance model from ticket 0002.
9. **`attachments`** — `id, page_id, s3_key, filename, mime, size, uploaded_by`. Links to the file block in the doc by id.
10. **Search support** — `pages.body_text` + a `tsvector` index; trigger to keep it fresh on save.

Decisions to land here:

- **Title location:** is the page title stored in the `pages` row, in the Y-doc, or both (and reconciled which way)? State the choice and the reconciliation direction.
- **Tree representation:** adjacency list (`parent_id`) confirmed, vs. materialized path / closure table — pick one with rationale for the sidebar-tree and permission-inheritance queries it must serve.
- **Principal polymorphism:** how to model `shares.principal` pointing at either a user or a group (polymorphic FK, or two nullable FKs, or a `principal_type` discriminator) — pick and justify.
- **Soft-delete:** do folders/pages get a `deleted_at` (trash) or hard-delete? (See map fog; this ticket decides it as a schema concern.)
- **Indexing strategy** for the two hot paths: (a) sidebar tree render ("children of folder F in workspace W"), (b) effective-permission check ("all shares on the path from workspace root to page P").

**Resolve by:** `/grilling` + `/domain-modeling`. The output is a schema spec (table-by-table) that a builder can turn into migrations, plus the named decisions above explicitly answered. **Blocked by ticket 0002** — the inheritance/role rules determine the shape of `shares` and the indexes that serve them.

## Notes

- This schema is what every backend query and every permission check reads. Getting the tree representation and the shares shape right here prevents painful migrations later.
- The Y-doc (`page_docs`) is deliberately out of relational normalization — do not decompose it into block rows (that decision is already made and recorded on the map).

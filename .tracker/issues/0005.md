## Question

The editor is **BlockNote** (decided). This ticket resolves **what v1 ships inside the editor** — the product-level scope of blocks. BlockNote ships a rich default set, so most of this is "accept defaults vs. trim/extend." Land each:

1. **Block-type list for v1.** Confirm the exact set. Recommended baseline (all BlockNote defaults): paragraph, H1–H3, bulleted list, numbered list, todo/checkbox, quote, code, divider, image, file, table. Trim or extend — state the final list.
2. **Nested-page blocks.** A Notion hallmark: any block can be a *link to another page*, and pages can be nested inside pages (a "sub-page" block that opens a new doc). This is central to "nested pages" being a first-class feature. **In or out for v1?** (Recommend in — it's a listed feature — but confirm, because it adds editor + tree-model coupling.)
3. **Slash menu & drag handle.** Use BlockNote's default slash menu and block-drag handle, or customize the slash menu's items/order? (Recommend defaults for v1.)
4. **Custom block types.** Does v1 need any app-specific block beyond BlockNote's defaults? (e.g. a "workspace-group mention," an "attachment gallery," a "kanban" — none of these are in the feature list, so recommend **none** for v1; flag that any future custom block requires ProseMirror schema work.)
5. **Text formatting depth.** Confirm the inline-formatting set: bold, italic, underline, strikethrough, inline code, link. Any others (color, highlight) in v1? (Recommend the standard six; defer color/highlight.)
6. **Markdown input / paste behavior.** BlockNote supports markdown shortcuts and paste. Confirm this is on by default — no decision likely, but state it so the spec is complete.

**Resolve by:** `/grilling`. Output: the v1 block-type spec (a list), the nested-page-block decision with rationale, the inline-formatting set, and explicit "deferred to post-v1" notes for anything trimmed.

## Notes

- The **nested-page-blocks** decision (item 2) feeds back into the data model (ticket 0003): if a page can be nested inside another *as a block*, then the `pages.parent_page_id` relationship and the Y-doc must agree on who owns the nesting edge. Surface this coupling.
- Text-formatting depth is mostly free (BlockNote defaults); the real product decision is nested-page blocks.

## Resolution — 2026-07-28

All six questions resolved. Editor is **BlockNote** (decided on the map). This
ticket locks v1 *editor scope* — and the user **deliberately widened** it beyond
the original feature list (confirmed in grilling), accepting the extra build
cost. That widening is recorded below as a conscious decision, not an accident.

### Decisions locked

1. **Block-type list for v1** — BlockNote defaults + the necessary custom blocks
   + the widened set:
   - **BlockNote defaults:** paragraph, H1, H2, H3, bulleted list, numbered list,
     todo/checkbox, quote, code, divider, table.
   - **From ticket 0007 (attachments):** image block (inline), **file block**
     (custom: icon + filename + size + download link).
   - **This ticket — nested pages:** **sub-page block** (custom; see item 2).
   - **This ticket — widened scope (user-confirmed):** **callout**, **toggle**,
     **@mention** (@user + @page), **embed** (YouTube/Figma/etc.).
2. **Nested-page blocks — YES in v1.** A page can be nested inside another page
   as a sub-page block, opening a new Y-doc; the tree nests via
   `pages.parent_page_id` (ticket 0003). **Ownership of the edge:** the
   **backend** owns it — the editor requests "insert sub-page here," the backend
   creates the `pages` row with `parent_page_id` set and returns the new
   `pageId`, then the editor inserts a block `{ type:'subpage',
   attrs:{ pageId, title } }` referencing it. This keeps the Y-doc and the
   relational tree consistent (the doc never owns a page-creation side effect).
3. **Slash menu & drag handle — BlockNote defaults** for v1 (no customization
   of the slash menu's items/order; revisit if UX testing wants changes).
4. **Custom block types — the widened set** (sub-page, file, callout, toggle,
   mention, embed) on top of BlockNote defaults. See "Build-cost notes" below.
5. **Text formatting — six marks + color + highlight** (user-confirmed widening):
   bold, italic, underline, strikethrough, inline code, link, **+ text color,
   + highlight (foreground + background)**. Defer nothing further (alignment
   comes with BlockNote defaults).
6. **Markdown input / paste — on by default** (BlockNote default; no decision
   needed, stated for spec completeness).

### Build-cost notes (the widened scope is NOT free)

These are flagged so the build effort plans realistically; they do not re-open
the decision:

- **Color/highlight** — extends BlockNote's mark schema + a color-picker toolbar
  surface. Modest.
- **Callout, toggle, embed** — each is a custom block: ProseMirror node schema +
  a React render component + slash-menu entry. Embed additionally needs an oEmbed
  / URL-to-embed resolver (a small mapping for YouTube/Figma/etc.).
- **@mention (@user + @page)** — the heaviest addition:
  - **@user** queries the workspace's members + groups (ticket 0002's
    `workspace_members` / `groups` / `group_members`), scoped to who the current
    user can see.
  - **@page** queries page titles — reuses the **FTS index from ticket 0008**
    (`search_tsv`), scoped by the effective-permission CTE.
  - Both need a popup query UI, a mark/node to store the mention
    (`{ userId }` / `{ pageId }`), and a resolver that renders the current
    name/title at read time (so renames propagate).
  - Post-v1 features that mentions often imply (notifications on @user) are
    **still out of scope** (notifications are on the map's Out-of-scope list) —
    v1 mentions are inert references, not notification triggers.

### Deferred to post-v1

- Further custom blocks (kanban, gallery, database/table-as-data, sync block).
- @mention notifications (mentions are inert references in v1).
- Per-block color theming beyond inline marks.

### Downstream impact

- **0003 (data model)** — `pages.parent_page_id` is used (confirmed, already in
  schema). Mentions store `{ userId }` / `{ pageId }` inside the Y-doc (no new
  relational table — they're inline content, resolved at render).
- **0008 (search)** — @page mention's typeahead reuses the `search_tsv` FTS index
  + permission scoping; no new index needed.
- **0009 (monorepo)** — all custom blocks + the mention query endpoints live in
  `apps/web` (BlockNote config) and `packages/ui`; the embed resolver is a small
  `packages/shared` utility. The editor is the single most code-heavy area of v1.
- **0002** — @user mention's typeahead reuses workspace member/group queries.

### 🔒 Security requirements (added post-resolution — see `research/SECURITY-REVIEW.md`)

The widened scope (embeds, mentions) adds real attack surface. These are mandatory:

1. **Embed block = iframe → XSS/clickjacking surface.** The embed block renders an
   iframe from a URL. Requirements: (a) embed URLs must match a **domain
   allowlist** (YouTube, Vimeo, Figma, Loom, …) — reject unknown providers;
   (b) the iframe carries a restrictive `sandbox` attribute (never
   `allow-scripts` + `allow-same-origin` together); (c) URL scheme allowlisted to
   https. An unrestricted embed iframe is XSS.
2. **URL-scheme validation on all URL-bearing blocks.** Embed, link, and image
   blocks take a URL attribute. Validate the scheme on render — **reject
   `javascript:` and `data:`** on image/link/embed `src`/`href`. (BlockNote
   sanitizes via ProseMirror schema, but custom blocks must enforce this in
   their render component, not rely on the editor alone.)
3. **Mention typeahead must use the permission CTE.** `@page` and `@user`
   typeahead queries must scope results by `can_read` / workspace membership —
   confirm the typeahead doesn't leak page titles or member names the user
   can't see. Reuse the same permission-scoped queries as search/sidebar.
4. **Paste hardening.** A paste of a pathologically large doc is bounded by the
   per-page Y-doc size cap (ticket 0003). Pasted HTML is sanitized by BlockNote's
   schema; watch for custom-block injection via pasted JSON and reject
   unrecognized block types.

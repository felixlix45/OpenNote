## Question

v1 attachments are scoped: **upload to S3-compatible storage, drag/paste to upload, images render inline as image blocks, other files become file blocks with download links, per-workspace quota + max file size.** This ticket resolves the specifics:

1. **Storage provider & abstraction.** Confirm the **S3-compatible** abstraction (AWS SDK v3 against any S3 endpoint) as the single storage interface, with concrete *default* providers per deployment style:
   - Self-host default: **MinIO** (bundled in docker-compose).
   - Managed options: **Cloudflare R2** (no egress fees) or AWS S3.
   State that the app talks to an S3 endpoint via env vars (`S3_ENDPOINT`, `S3_BUCKET`, credentials) and is provider-agnostic.
2. **Quotas & limits.** Concrete v1 numbers. Recommend:
   - Max file size: **25 MB** (Notion's free-tier-ish; tunable via env).
   - Per-workspace quota: **configurable, default 5 GB**, enforced at upload time (sum of `attachments.size` for the workspace < quota).
   Confirm or adjust the numbers; the mechanism (check-then-upload) is what matters.
3. **Access control on downloads.** Files must respect the page's permission — a leaked URL must not bypass RBAC. Decide between:
   - **Short-lived signed URLs** (S3 `getSignedUrl`, e.g. 5–15 min TTL), minted by the backend after a permission check, **or**
   - **Cookie-authed streaming proxy** (backend streams the bytes after checking the page permission).
   **Recommend signed URLs** (simpler, offloads bytes to S3) — confirm, and note the URL must encode the page/attachment id so the backend can re-check permission on mint.
4. **Upload flow.** Two viable patterns:
   - **Backend-mediated:** client requests a presigned PUT URL from the backend (which checks quota + write-permission on the page), uploads directly to S3, then notifies the backend to create the `attachments` row.
   - **Direct multipart through backend:** bytes flow through the app server.
   **Recommend presigned-URL (direct-to-S3)** — keeps the app server out of the byte path. Confirm.
5. **Block integration.** How does an uploaded file become a block? Confirm: backend returns an attachment id + URL; the editor inserts a BlockNote image/file block carrying the attachment id; the block's URL is a signed-URL endpoint, not the raw S3 key.
6. **Quarantine / type checking.** Does v1 validate file type (allowlist of MIME) or scan anything? **Recommend** a permissive allowlist by extension/MIME in v1 (no AV); flag AV scanning as post-v1.

**Resolve by:** `/grilling`. Output: the storage abstraction + default providers, the concrete quota/size numbers, the access-control mechanism (signed URLs vs proxy), the upload flow, and the block-integration step.

## Resolution — 2026-07-28

All six questions resolved. The `attachments` table shape is already in the
schema (ticket 0003); this ticket locks the storage layer, limits, and flows.

### Decisions locked

1. **Storage provider & abstraction** — a single **S3-compatible** interface
   via the **AWS SDK v3** (`@aws-sdk/client-s3` + `@aws-sdk/s3-request-presigner`),
   configured by env (`S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`,
   `S3_SECRET_ACCESS_KEY`, `S3_FORCE_PATH_STYLE`). Provider-agnostic. Defaults:
   - **Self-host default: MinIO** (bundled in the dev/prod `docker-compose.yml`).
   - Managed options: **Cloudflare R2** (no egress fees) or AWS S3.
2. **Quotas & limits** — **25 MB / file, 5 GB / workspace** default, both
   env-tunable (`S3_MAX_FILE_SIZE_BYTES`, `WORKSPACE_DEFAULT_QUOTA_BYTES`;
   `workspaces.storage_quota_bytes NULL` = unlimited). Enforced at
   upload-request (sum + claimed_size > quota → 413) and re-checked at
   upload-complete against the true size.
3. **Access control** — **short-lived S3 signed GET URLs (10-min TTL)**, minted
   by the backend **after** running `can_read(user, page)` (owner/admin
   fast-path). Bucket stays **private** (no public reads); app server stays out
   of the byte path. A leaked URL is useless after TTL and never bypasses RBAC
   (minting requires an authenticated, authorized session).
4. **Upload flow** — **presigned PUT, direct-to-S3**: client requests a
   presigned PUT URL from the backend (which checks write-permission on the page
   + quota), uploads bytes directly to S3 (Content-Length bounded by the size
   limit), then notifies the backend to create the `attachments` row (re-checks
   quota, records the true `size_bytes`).
5. **Block integration** — backend returns `{ attachmentId, signedUrl }`;
   the editor inserts a **BlockNote image block** (for image MIME) or a
   **file block** (icon + filename + size + download link) carrying the
   `attachmentId`. The block's `src`/`href` points at the signed-URL endpoint
   (`/api/attachments/:id/url`), **not** the raw S3 key — so every view
   re-mints a fresh signed URL through the permission check.
6. **Type validation** — **permissive MIME/extension allowlist** at
   upload-request (pdf, docx, xlsx, pptx, txt, md, csv, json, png/jpg/gif/webp,
   zip/tar/gz, mp4/mov, mp3/wav, …). No content sniffing, no AV in v1
   (ClamAV sidecar or cloud scan hook is post-v1).

### Security note (must implement)

**Stored-XSS via inline SVG/HTML:** SVG and HTML uploads can carry `<script>`.
They **must not** be rendered inline from the app's origin. The signed-URL
endpoint sets `Content-Disposition: attachment` and a sandboxed/non-HTML
`Content-Type` for these types (and generally for any non-image type), so the
browser downloads rather than executes. Image types (`png/jpg/gif/webp`) render
inline safely; `svg` is treated as a download, not an inline image, in v1.

### The two endpoints (spec)

```
POST /api/pages/:pageId/attachments        (session; needs can_write on page)
  body: { filename, mimeType, sizeBytes }
  -> check ext/filename against allowlist            (else 415)
  -> check sizeBytes <= S3_MAX_FILE_SIZE_BYTES       (else 413)
  -> check quota: sum(size_bytes)+sizeBytes <= quota (else 413)
  -> create attachments row (status=pending), s3_key = `${wsId}/${id}/${filename}`
  -> mint presigned PUT (Content-Length=bounded, ttl=5min)
  -> 200 { attachmentId, uploadUrl }

GET  /api/attachments/:id/url              (session; needs can_read on page)
  -> load attachment -> page
  -> can_read(U, page)?  no: 403
  -> mint presigned GET (ttl=10min), Content-Disposition per type
  -> 200 { url, expiresAt }

POST /api/attachments/:id/complete         (client confirms upload finished)
  -> HEAD the S3 object to confirm presence + real size
  -> re-check quota with real size; mark row status=ready
  -> return { attachmentId, signedUrl }  (client inserts the block)
```

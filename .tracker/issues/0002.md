# Permission & sharing model: inheritance, roles, groups, overrides

- **Label:** `wayfinder:grilling`
- **Status:** closed (resolved 2026-07-28)
- **Parent:** [0001 — MAP](./0001.md)
- **Blocking:** [0003](./0003.md), [0008](./0008.md), [0010](./0010.md), [0007](./0007.md)
- **Assignee:** ZCode (working the map)

## Question

This map has committed to the **full Notion-style permission engine**: multi-tenant workspaces, workspace roles, **groups** (many-to-many with users, scoped to a workspace), and per-resource shares to users *or* groups with inheritance down the folder→page tree. This ticket resolves the **exact semantics** that the data model and the auth checks must implement. Decisions to land here, one at a time:

1. **Roles.** Which workspace roles exist (e.g. `owner / admin / member / guest`), and what is the capability set of each? Is "owner" a per-resource concept or only at workspace level?
2. **Resource types that can be shared.** Workspace, folder, page — which carry their own ACL? Can a *group* be a share target on every shareable resource?
3. **Inheritance.** How does a share propagate down the tree? When a page sits under a shared folder, does the page's effective permission = **union** of its own shares and all ancestors', or does the nearest explicit share **override** inherited ones?
4. **Group membership resolution.** Live (membership evaluated at check time) or cached? When a user is removed from a group, when do their grants evaporate — immediately, or on next session/doc load?
5. **Denials.** Is there an explicit "deny" (blocklist) concept, or only grants (allowlist)? (Notion is allowlist-only; deny adds power but doubles the model.)
6. **Public sharing.** Is "anyone with the link" in v1, or only named users/groups? (Affects the auth check on every doc load and the share UI.)
7. **Guests / external users.** Can someone outside the workspace be granted access to a single page, or must they join the workspace first?

**Resolve by:** `/grilling` + `/domain-modeling`. Produce a precise spec the data-model ticket can encode: a list of role→capability mappings, the inheritance rule, the group-membership rule, and a one-paragraph "effective permission" algorithm (how to answer "can user U perform action A on resource R").

## Notes

- This is the densest fog on the map and **blocks** the data-model ticket (can't design the permission tables without these rules) and the realtime-auth ticket (the effective-permission algorithm is what Hocuspocus's `onAuthenticate` runs).
- Real-time is decided (in scope) — so the algorithm must be cheap enough to run on every WebSocket connection and doc load, and produce a stable answer despite concurrent share changes.

## Resolution — 2026-07-28

All seven sub-questions resolved via grilling + domain-modeling. The ubiquitous
language is captured in `CONTEXT.md` at the repo root. What follows is the
precise spec the downstream tickets encode.

### Role set
**Guest / Member / Admin / Owner** — strict capability ladder.
- **Guest** — access defined *entirely* by per-resource Shares; cannot browse
  the Workspace tree; invited from outside via a Share.
- **Member** — default for joined users; effectively Editor everywhere via the
  *all-members* group (open-workspace rule, below).
- **Admin** — manage settings, members, Groups. Cannot delete/transfer Workspace.
- **Owner** — ≥1 per Workspace; everything Admin does + delete + transfer.

Owner/Admin **bypass** the Share model entirely (full manage on everything).

### Permission levels (per-resource axis)
**Reader / Commenter / Editor** (+ implicit *none*). Granted by a Share to a
User or Group on a Folder or Page.
- **Commenter is reserved** — comments are post-v1, so it behaves as Reader
  in v1. The level exists in the enum for forward compatibility.

There is **no Full-Access/reshare level in v1** — only Owner/Admin create Shares.

### Inheritance rule — union, strongest grant wins
A principal's **effective permission** on a resource = the **maximum** Permission
level granted anywhere along the path from the Workspace root down to that
resource, across **direct Shares + Group Shares**, evaluated **live**.

```
strength:  Editor > Commenter > Reader > none

effective(User U, Resource R):
  if U is Owner/Admin of R.workspace: return "manage"   # bypass
  grants = [ s.level
             for s in shares
             where s.resource ∈ path(workspace_root → R)
             and ( s.principal = U
                   or s.principal ∈ groups_of(U) ) ]     # live join
  return max(grants) default none
```

Consequences (decided):
- A Share on a child **never downgrades** a stronger ancestor Share.
- To **revoke**: delete the Share, remove the User from the Group, or lower
  the Role. (No Deny concept — allowlist only.)
- **Group membership is evaluated live** at check time (one indexed join on
  `group_members` keyed by `user_id`); no membership cache, no staleness.

### Open-workspace rule
The Workspace root carries an implicit **Editor Share to the all-members
group** (auto-maintained: every non-Guest Member). So:
- **Member** → Editor on every resource by default (no per-resource grants needed).
- **Guest** → only what's explicitly Shared to them.
- **Owner/Admin** → bypass.

Privacy *between members* is achieved with separate Workspaces, not per-page
restriction (consistent with union + no-deny + open-workspace).

### External users (Guests)
An external user is invited to the Workspace as a **Guest** via a per-resource
Share: ADMIN/OWNER enters their email → invite → the outsider creates an
account (or signs in) → added to `workspace_members` with `role=Guest`. Their
sidebar shows only explicitly-shared resources; their effective permission is
the union of their per-resource Shares (the Guest role grants nothing).

### Public sharing
**Out of scope for v1.** Every Share targets a known principal (User/Group).
No anonymous doc-load path, no share-URL surface. (Add later as a
resource-level flag that flips doc-load auth to "allow anonymous read".)

### Cost budget (for ticket 0010)
The algorithm is **O(depth × principals)** indexed lookups — walks the path
`workspace_root → R`, collects matching Shares. For realtime, this runs in
`onAuthenticate` on connect; per the research findings (ticket 0004), there is
**no built-in periodic re-auth in Hocuspocus**, so live revocation in v1 is
**accepted-stale until reconnect** (post-v1 can add a 60s re-check). This is
explicitly a v1 simplification, not a bug — ticket 0010 records the decision.

### Downstream impact

- **0003 (data model)** — encode: `workspace_members(role enum: guest/member/admin/owner)`,
  `groups` + `group_members(workspace_id, user_id)`, an implicit *all-members*
  group (or a sentinel share), `shares(resource_type, resource_id,
  principal_type, principal_id, level enum)`, with indexes serving
  (a) "all Shares on path workspace_root → R, for principals ∈ {U} ∪ groups(U)"
  and (b) sidebar "children of folder F visible to U". Confirm identity scope
  (global User) with ticket 0006.
- **0010 (realtime auth)** — `onAuthenticate` runs the effective-permission
  algorithm; `none` → reject connection; `reader/commenter` →
  `connection.readOnly = true`; `editor` → read/write. Live revocation is
  reconnect-based in v1 (see Cost budget).
- **0007 (attachments)** — the signed-URL mint endpoint runs the same
  effective-permission check before signing; `none` → 403.
- **0008 (search)** — result scoping = "pages where effective(User, page) ≥
  Reader"; implement inline as a join against the path-Shares (recommend
  inline for v1, see ticket 0008).
- **Unblocks**: 0003, 0007, 0008, 0010 leave the blocked set as 0002 closes.
